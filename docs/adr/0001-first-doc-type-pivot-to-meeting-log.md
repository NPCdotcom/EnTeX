# ADR-0001: 最初の文書種をサークル月次報告書から部会ログのフォーマット化へ差し替える

## Context

charter §5 のMVPおよび§11の着手順1は、最初の文書種（doc-package）として「サークルの月次活動報告書」を仮に置いていた（`packages/circle-monthly-report/`）。理由は charter §3 の Aster 提案どおり、我々自身が当事者であり実物の様式が手に入るという想定だった。

[issue #11](https://github.com/NPCdotcom/EnTeX/issues/11)（実物の様式に合わせて月次報告書パッケージを直す）の対応過程で、実物の様式を確認しようとしたところ、**情報技術研究部には月次報告書を学生課へ提出する運用自体が存在しない**ことが判明した。issue #11 自身が「題材そのものが無い場合」の節で、代替候補（立花祭の出展申請・実施報告、部の予算申請書・決算書）を挙げて題材の差し替えを想定していた。

これを受けて、ユーザーは方針を修正し、サークル内の**部会ログ（議事録）のフォーマット化**へ焦点を当てることを決めた（2026-09-12の指示）。部会ログはissue #11が挙げた代替候補（立花祭申請、予算書）とは異なる、新たな第三の選択肢である。

なお、この時点でプロジェクトは着手順1（CLI, PR #8）・着手順2の一部（`entex.pipeline` 共通化 + CLI 移行, PR #10）まで進んでおり、`renderer` / `entex.pipeline` / CLI / API設計（`docs/design/programs/api.md`）は文書種の中身に依存しない形で実装済みである（charter §8 の境界: `renderer` は IR の出どころもパッケージの中身の詳細も知らない）。

## Decision

- 最初の文書種（doc-package）の題材を「サークルの月次活動報告書」から「サークルの部会ログのフォーマット化」に変更する。
- charter §3（利用者）・§5（MVP）・§11（着手順・Open questions）を更新し、この決定と経緯を記録する（本ADRへの相互リンクを含む）。
- `packages/circle-monthly-report/` および `docs/requirements/circle-monthly-report/{要求,要件}.md` は、実物確認前の**仮定に基づくスキーマ設計・renderer実装の検証**という役割を果たした成果物として残す。削除はしない。冒頭に本ADRへのリンクと「新規の文書種としては開発を継続しない」旨の注記を追加する。
- 部会ログの具体的な様式（頻度、欄構成、保管・共有方法、承認の要否など）は本ADRの時点では未確定。**ユーザーから追って提示される情報を受けてP1（`docs/requirements/`配下に新しい要求.md）からやり直す**。
- `packages/circle-monthly-report/` を改修して部会ログ用に転用するか、別スラッグの新規パッケージ（例: `circle-meeting-log/`）として追加するかは、P1要求定義の中で決める。charter §4の設計核（文書種を1つ増やすのに本体のコードを1行も変えずに済む）の判定にはどちらでも影響しない。

## Consequences

### Positive

- 実在しない運用を前提にした要求・スキーマ・レイアウトを作り込む手戻りを、詳細設計（P3以降）に進む前に止められた。
- `renderer` / `entex.pipeline` / CLI / API という本体側の実装（charter §8 の境界を守って作られている）は文書種の中身に依存しないため、作り直しが不要。着手順2（API化）の作業は影響を受けずに継続できる。
- `packages/circle-monthly-report/` はrenderer実装のための「型の語彙を一通り使う仮想的な題材」としては引き続き有効な参考資料になる（`docs/design/elements/ir-type-vocabulary.md` の精査に使われた）。

### Negative / trade-offs

- `docs/requirements/circle-monthly-report/{要求,要件}.md` は実在しない運用を前提に書かれた要求・要件として残り、今後は「参考・reference」として扱う必要がある。読み手が現行の一次情報だと誤解しないよう、各ファイル冒頭に注記を追加する運用コストが生じる。
- `docs/design/elements/ir-type-vocabulary.md` の Assumptions（§7 など）は月次報告書を題材にした精査結果であり、部会ログの実物に照らすと再判定が必要になる可能性がある（時刻欄の要否など）。これはユーザー提示の情報を受けて改めて判断する。
- MVPの成功指標（charter §6「TeXを知らない人が、口頭の説明なしで報告書を1本PDFにできる」）の実証相手が変わるため、実証のタイミングが遅れる。

## Facts

- issue #11 が「情報技術研究部は活動が月1回あるかないかの規模なので、月次報告書の運用自体が存在しない可能性がある」と明記しており、実際にその通りだった。
- `renderer` / `entex.pipeline` / CLI（PR #8, #10）は文書種非依存の実装として完成済みで、本ADRの決定による手戻りの対象外。
- `packages/circle-monthly-report/` の`schema.json`・IR例12件・`template.tex.j2`・スタイルは、実物に基づかない仮定として最初から明記されていた（同READMEの「未確認・仮定」節）。

## Assumptions

- 部会ログのフォーマット化が、charter §3 の「大学のサークルの運営者」という利用者層・優先度（高）に引き続き当てはまる。ヒアリングによる検証はまだ行っていない。
- 部会ログはサークル内部の記録であり、月次報告書のような外部（学生課）への提出物ではないという理解。これはユーザー提示の情報で確定させる。
- `packages/circle-monthly-report/` を土台に改修する方が、ゼロから新規パッケージを作るより手戻りが少ないと見込んでいるが、実物の欄構成次第では新設の方が単純になる可能性もある。

## Open questions

**すべて解決済み**（2026-09-12）。[issue #14](https://github.com/NPCdotcom/EnTeX/issues/14) の実物47本の全数集計で様式が判明し、残りもそこから決まった。本ADRの Decision そのものは変わっていない。以下は消し込みの記録であり、各項の正本は charter の該当節である。

| 当時の問い | 答え | 正本 |
|---|---|---|
| 部会ログの具体的な様式（頻度・欄構成・行数の上限・保管形態・承認フローの有無） | 頻度は週1回程度。メタ情報はNotionのページプロパティ3つ。節は3つ（アナウンス44・活動報告34・次回予告4）に収束。本文主体のため行数の上限は無し。承認・確認のフローは無い | charter §3 のAsterの追記 |
| `packages/circle-monthly-report/` を改修するか、新規パッケージとして追加するか | **新規 `club-meeting-log` を起こす。** 月次報告書は欄が並ぶ書類、部会ログは本文主体で、共通する欄がほぼ無い。`circle-monthly-report` は型語彙を一通り使う参考資料として上書きせず残す | charter §11 決着済み |
| `ir-type-vocabulary.md` §7 を再判定する必要があるか | **一部要る。** `image` は前倒しが必要（直近の回ほど画像が主役で、最新の回は本文がほぼ画像だけ）。`time` / 小数 / 表は実測0件のため据え置きでよい。加えて本文用に `document` 型を足す | [issue #21](https://github.com/NPCdotcom/EnTeX/issues/21) |
| 着手順3の2つ目として扱うか、1つ目を差し替えるか | **1つ目の差し替え。** `circle-monthly-report` は実物に基づかないため charter §6 の合否判定の材料にならない。判定は実物に基づく2つ目（着手順3b）で行う | charter §11 着手順 |

上の Assumptions のうち「`packages/circle-monthly-report/` を土台に改修する方が、ゼロから新規パッケージを作るより手戻りが少ない」は**外れた**。実物の欄構成が想定と重ならず、新設の方が単純だった。同じ項が但し書きで残していた可能性の方が当たったことになる。

様式が判明した後、入力形式そのものも決まっている（Notionのエクスポートを第一の経路にし、メタ情報を人間に書かせない）。本ADRの範囲外だが、`docs/requirements/club-meeting-log/` のP1要求定義はその前提で書く。詳細は charter §5.2 と [issue #20](https://github.com/NPCdotcom/EnTeX/issues/20)。

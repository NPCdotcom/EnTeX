# IR 型の語彙

`ir-schema`（charter §8）が扱う **値の種類（型）** を決める。文書種パッケージの `schema.json` は、この語彙に含まれる型だけを使ってフィールドを宣言する。題材は最初の文書種「サークルの月次報告書」（charter §5、**2026-09-12以前**）。

> **2026-09-12 注記（[issue #11](https://github.com/NPCdotcom/EnTeX/issues/11) / [ADR-0001](../../adr/0001-first-doc-type-pivot-to-meeting-log.md)）**: 月次報告書を学生課へ提出する運用自体が存在しないと判明し、最初の文書種はサークル内の部会ログのフォーマット化に差し替えた。ここで決めた型の語彙（§1、11型）自体は文書種に依存しない設計で、そのまま使える見込み。ただし月次報告書を題材にした前提の上に立つ Assumptions（特に §7「語彙に入れなかったもの」）は、部会ログの実物が判明した時点で再判定する。

> NPC の原案（2026/9/12）は §1 の表の出発点。以下は原案を精査した結果で、変更点は §2 に理由つきで書いた。

## 0. 前提

- IR は「見た目を含まない中身」だけを表す（charter §10）。型は **内容の種類** を表し、表示の仕方（和暦・カンマ区切り・☑）は持たない
- 型の語彙は **閉じた小さな集合** にする。1 つ型を足すごとに「検証」「フォーム部品」「TeX への変換（エスケープ・整形）」の 3 つを必ず用意する必要があるため
- 型（値が何であるか）と、フィールド属性（必須か・上限は・導出値か）は **別の軸** として扱う（§3）

## 1. 語彙（精査後）

| 型 | 表すもの | JSON 表現 | 検証（型に固有のもの） | 月次報告書での例 |
|---|---|---|---|---|
| `text` | 1行の短い文字列 | string | 改行・制御文字を含まない。NFC 正規化 | 団体名・氏名・役職・場所 |
| `rich_text` | 段落と箇条書きだけを持つ長文 | object（§2.2） | ブロックは `paragraph` / `list` の2種。入れ子なし。行内装飾なし | 活動概要・所感 |
| `month` | 年月 | string `"2026-08"` | `^\d{4}-(0[1-9]\|1[0-2])$` | 報告対象月 |
| `date` | 日付 | string `"2026-08-03"` | ISO 8601 の日付部のみ。実在する日付 | 開催日・提出日 |
| `integer` | 個数・人数 | integer | 既定で `minimum: 0`（フィールド側で上書き可） | 参加人数・在籍数 |
| `money` | 金額（円） | integer | **符号あり**。非負にしたい場合はフィールド側で `minimum: 0` | 収入額・支出額・繰越・残高 |
| `enum` | 決められた選択肢の1つ | string（選択肢の `value`） | `value` は英語スネークケース。表示名 `label` はスキーマ側に持つ | 収支区分（`income` / `expense`） |
| `boolean` | 有無（2値） | bool | null 不可。「未実施・該当なし」が要るなら `enum` を使う | 監査済みか |
| `object` | 名前つきの組 | object | 子はスカラーまたは `object`。深さは 2 まで | 作成者（役職 + 氏名） |
| `row_list` | 同じ形の行の並び（＝表） | array\<object\> | 行の子は **スカラーのみ**（`object` / `row_list` / `rich_text` / `list` 不可）。順序は入力どおり | 活動実績・会計明細 |
| `list` | 値の並び（＝箇条書き） | array\<scalar\> | 要素の型は `text` / `enum` / `date` / `integer` のいずれか1つ | 次月の予定・活動区分（複数選択） |

スカラー = `text` `month` `date` `integer` `money` `enum` `boolean`。それ以外（`rich_text` `object` `row_list` `list`）は複合。

## 2. 原案からの変更点と理由

### 2.1 `money` を「非負整数」から「符号あり整数」へ

原案は非負整数だった。収入・支出を正の額で持ち、向きは `enum` で表す設計自体は妥当で維持する。ただし **前月繰越・残高は赤字で負になり得る**。型として非負を固定すると、残高フィールドが `money` で表せず `integer` に逃げることになり、「金額である」という情報が落ちる。

→ 型としては符号あり。非負であるべきフィールド（明細の `amount`）は `minimum: 0` を **フィールド属性** で付ける。

補足: 円は小数単位を持たないので integer で正しい。通貨は当面 JPY 固定。将来の一般化は `currency` 属性の追加で対応でき、いまは入れない。

### 2.2 `rich_text` の object 構造を決める

原案は「object」とだけあった。構造が決まらないと検証もフォームも TeX 変換も書けないので、次を提案する。

```json
{
  "blocks": [
    { "type": "paragraph", "text": "8月は合宿と新歓の準備を並行して進めた。" },
    { "type": "list", "items": ["合宿（8/3–8/5）", "新歓ビラの作成"] },
    { "type": "paragraph", "text": "参加率は前月より改善した。" }
  ]
}
```

- ブロックは `paragraph` と `list` の2種のみ。箇条書きの入れ子はしない
- 行内装飾（太字・下線・リンク）は持たない。強調が体裁として必要なら文書種パッケージ側で決める（charter §10「見た目を含まない」）
- `text` / `items[]` の各要素は `text` と同じ検証（改行なし・NFC）

**別案（退けたが記録する）: 記法つき文字列。** 空行で段落、行頭 `- ` で箇条書き、という Markdown の部分集合を1本の string で持つ。JSON を手で書くときと CSV のセルに収めるとき（着手順 5）に楽だが、**誰が解釈するか** が問題になる。renderer が解釈すると renderer が記法を知ることになり、テンプレートが解釈すると TeX 側にパーサを書くことになる。

→ IR の正本は上の block 構造とする。記法つき文字列は `form-ui` / `data-import` が IR を **作る側** で受け付けてよい（block へ変換して IR に渡す）。renderer には block しか届かない。これで charter §8 の境界（renderer は IR の出どころを知らない）を保てる。

### 2.3 `row_list` の行はスカラーのみ

原案には制約がなかった。行の中に `object` や `rich_text` が入ると、(a) TeX の `tabular` に素直に落ちない、(b) フォームが表形式で出せない、(c) CSV の1行1文書（着手順 5）と噛み合わない。3つとも同じ理由で **行 = フラットなスカラーの組** が自然。必要が出たら 2 つ目の文書種で再判定する。

あわせて `max_items` を持てるようにする。**固定書式の PDF で表が長すぎると必ずレイアウトが崩れる** ため、文書種パッケージが「この表は最大 N 行」と宣言できる必要がある。何行で崩れるかは体裁の知識なので、値は `src/entex/` ではなく `packages/<slug>/schema.json` に置く。

### 2.4 `list` の要素型を限定

原案は「array\<scalar\>」だった。全スカラーを許すと `money` の列や `boolean` の列も合法になるが、用途が思い当たらない。`text`（次月の予定）と `enum`（活動区分の複数選択）が主で、`date` `integer` は補助的に許す。`month` `money` `boolean` は当面除外。

`list<enum>` があるので、原案にない「複数選択」は新しい型を足さずに表せる。

### 2.5 `boolean` は null を許さない

フォームでは「未確認」「該当なし」の第3状態が後から出てくることが多い。boolean を nullable にして 3 値化すると、テンプレート側で `true` / `false` / `null` の 3 分岐が必要になり、しかも `null` が「未入力」なのか「該当なし」なのか区別できない。

→ 3 値以上が要るフィールドは `enum`（例: `done` / `not_done` / `not_applicable`）で宣言する。boolean は厳密に 2 値。

### 2.6 `text` に正規化と改行禁止を入れる

「同じ入力からは常に同じ PDF が出る」（charter §4）ためには、見た目が同じで符号が違う文字列（結合文字と合成済み文字など）を同一に扱う必要がある。NFC 正規化を IR の検証段で行う。全角・半角の数字は意味が違い得るので **正規化しない**（入力どおり）。

1 行であることを型の意味とする。改行を含む値は `rich_text` を使う。

### 2.7 `integer` の既定を非負に

人数・個数に負はないので既定 `minimum: 0`。負を許すフィールド（差分・増減）はフィールド側で `minimum` を外す。

## 3. 型とは別の軸: フィールド属性

原案の表には無いが、`schema.json` を書くと必ず要るもの。型ではなく **フィールド** に付く。

| 属性 | 意味 | 備考 |
|---|---|---|
| `required` | 必須か | 既定 `true`。任意なら `false`。値が無いとき IR に **キーごと出さない**（`null` を使わない） |
| `label` | 利用者に見せる名前（日本語） | フォームとテンプレートが共用 |
| `description` | 補足説明・入力例 | フォーム用 |
| `default` | 初期値 | `month` の「今月」のような **動的な既定値は持たない**（決定性のため）。静的な値のみ |
| `derived` | 導出値 | §4 を参照 |
| `minimum` / `maximum` | 数値の範囲 | `integer` `money` |
| `max_length` | 文字数上限 | `text`。行が折り返すと崩れるフィールドに付ける（体裁側の知識なのでパッケージが決める） |
| `min_items` / `max_items` | 要素数の範囲 | `row_list` `list` |
| `pattern` | 追加の正規表現 | `text` の郵便番号など。使いすぎない |
| `items` | 要素の型 | `list` で必須 |
| `fields` | 子の定義 | `object` `row_list` で必須 |
| `options` | `{ value, label }` の並び | `enum` で必須 |

## 4. 導出値（合計・残高）をどう持つか

会計明細があれば **収入合計・支出合計・残高は行から計算できる**。IR にこれらを「利用者の入力」として持たせると、行と合計が食い違った文書が合法になる。決定性を保つには次のどちらか。

- **A. IR には行だけを持ち、合計は生成時に計算する。** 計算する場所は renderer の IR 正規化段（テンプレートに渡す直前）。テンプレート内で `sum` するのではなく、`derived: true` と `expr` をスキーマで宣言し、`src/entex/` の側が **文書種を知らずに** 評価する
- **B. IR に合計も持たせ、検証で一致を確認する。** API 越しに IR を受け取るとき（着手順 2）に、送り手が計算した値を照合できる利点がある

**決定: A を採る**（NPC・Aster 合意、2026/9/12）。理由: (1) 利用者に電卓を叩かせない、(2) 食い違う文書がそもそも作れない、(3) B は A に後から足せる（一致検証は A の計算結果と比較すればよい）。

これに伴う規則:

- 導出フィールドは `schema.json` で `derived: true` と `expr` を宣言する。**IR の入力に導出フィールドのキーが含まれていたら検証エラー**にする（黙って無視すると、送り手が「自分の値が使われた」と誤解する）
- 式は文字列ではなく **JSON の構造** で書く。パーサを書かずに済み、許す形が閉じる

```json
{ "sum": "finance.amount", "where": { "category": "income" } }
{ "count": "activities" }
{ "add": ["balance_carried", "income_total"] }
{ "sub": ["x", "expense_total"] }
```

| 形 | 意味 | 制約 |
|---|---|---|
| `{"sum": "<row_list>.<field>", "where": {...}}` | 行の数値フィールドの合計 | `field` は `integer` / `money`。`where` は任意で、`{ "<field>": "<value>" }` の等値条件のみ（複数キーは AND） |
| `{"count": "<row_list>"}` | 行数 | — |
| `{"add": [a, b, ...]}` / `{"sub": [a, b]}` | 加算・減算 | 引数はフィールド名（導出済みのものを含む）・整数リテラル・入れ子の式のいずれか。`sub` は 2 引数 |

導出フィールドの型は `integer` か `money`。導出同士の参照は許すが、循環は検証で拒否する（宣言順に評価すればよいので、参照先は自分より前に宣言されていること、を規則にする）。掛け算・割合・条件分岐は入れない。任意式の評価器を作り始めると文書種パッケージがプログラムになる。式の語彙が足りない文書種が出た時点で再検討する。

## 5. 型ごとの TeX 側の責務（IR には入れないが決めておく）

型が閉じているので、型ごとに「TeX への落とし方」を 1 つずつ用意すれば足りる。どちらの側が持つかを分ける。

| 型 | `src/entex/`（文書種を知らない） | `packages/<slug>/`（体裁を知っている） |
|---|---|---|
| `text` | TeX 特殊文字のエスケープ（必ず通す。AGENTS.md） | フォント・折り返し |
| `rich_text` | 各 block の文字列をエスケープ | `paragraph` → 段落、`list` → `itemize` 等への展開 |
| `month` `date` | 妥当性検証のみ | 和暦・西暦、区切り記号（`2026年8月` / `R8.8`） |
| `integer` `money` | 妥当性検証のみ | 3桁区切り、`¥` の有無、負数の表し方（`△` / `-`） |
| `enum` | `value` の検証 | `label` の表示 |
| `boolean` | 妥当性検証のみ | 「済 / 未」「☑ / ☐」 |
| `row_list` | 行数・各セルの検証とエスケープ | `tabular` の列定義、罫線 |

日付・金額の整形を `src/entex/` に入れたくなるが、それは体裁の知識である。Jinja2 フィルタとして提供するのは構わないが、**どのフィルタを使うかはテンプレートが選ぶ**。

## 6. 月次報告書の IR 例

上の語彙で最初の文書種を表した例。フィールド名は仮。

```json
{
  "organization": "○○大学 △△サークル",
  "report_month": "2026-08",
  "author": { "role": "会計", "name": "山田 太郎" },
  "submitted_on": "2026-09-05",
  "member_count": 24,
  "summary": {
    "blocks": [
      { "type": "paragraph", "text": "8月は合宿と新歓の準備を並行して進めた。" },
      { "type": "list", "items": ["合宿（8/3–8/5）", "新歓ビラの作成"] }
    ]
  },
  "activities": [
    { "date": "2026-08-03", "title": "夏合宿", "place": "長野県", "participants": 18 },
    { "date": "2026-08-20", "title": "定例会", "place": "第2会議室", "participants": 15 }
  ],
  "balance_carried": -3200,
  "finance": [
    { "date": "2026-08-01", "category": "income",  "item": "部費", "amount": 48000 },
    { "date": "2026-08-03", "category": "expense", "item": "合宿宿泊費", "amount": 36000 }
  ],
  "next_month_plan": ["新歓イベント（9/15）", "秋合宿の会場予約"],
  "remarks": { "blocks": [ { "type": "paragraph", "text": "参加率は前月より改善した。" } ] },
  "audited": false
}
```

`income_total` / `expense_total` / `balance` は IR に **含まれない**（§4 の A）。`balance_carried` が負なのは §2.1 の根拠。

運用を想定して網羅した版（スキーマ・正常系 6 件・異常系 6 件）は [`packages/circle-monthly-report/`](../../../packages/circle-monthly-report/README.md) にある。上の例は語彙の説明用の抜粋で、正本はそちら。

### 6.1 封筒（envelope）— IR がどの文書種のものかを自己申告する

IR の中身（`content`）だけを渡すと、受け取った側（CLI の `render`、API、将来のジョブ履歴）が「どのパッケージのどの版のスキーマで検証するか」を別経路で知る必要が出る。運用上は IR ファイル 1 つで閉じている方が扱いやすいので、次の封筒で包む。

```json
{
  "doc_type": "circle-monthly-report",
  "schema_version": 1,
  "content": { ...上の中身... }
}
```

| キー | 意味 | 規則 |
|---|---|---|
| `doc_type` | パッケージのスラッグ | `packages/<slug>/` と一致。英語ケバブケース |
| `schema_version` | パッケージの `schema.json` の版 | 1 以上の整数。上げる基準は下記。renderer は自分が知らない版を拒否する |
| `content` | 中身 | `schema.json` の `fields` に従う。**未知のキー・導出フィールドのキーは拒否**（打ち間違いと §4 の誤解を防ぐ） |

封筒は `ir-schema` の共通部分なので `schemas/ir/` 側の定義になる。`content` の形だけが文書種ごとに違う。

#### `schema_version` を上げる基準

判定の軸は1つ、**「それまで通っていた IR が通らなくなるか」**である。なるなら上げる、ならないなら上げない。

版が合わないと [`src/entex/ir/loader.py`](../../../src/entex/ir/loader.py) が中身を見る前に弾く（`文書の版（schema_version）が一致しません（期待: N、実際: M）。`）。上げれば既存の IR は例外なく書き直しになるので、上げずに済むものは上げない。

| `schema.json` への変更 | 版 | 理由 |
|---|---|---|
| 任意フィールドの追加（`required: false`） | 上げない | 書いていない IR がそのまま通る |
| `label` / `description` / `title` の変更 | 上げない | 検証に効かない |
| 制約の緩和（`max_length` を伸ばす、`minimum` を下げる、`max_items` を増やす） | 上げない | 通っていたものは通り続ける |
| `enum` の選択肢の追加 | 上げない | 同上 |
| 任意フィールドへの `default` の追加・変更 | 上げない | 検証は通る（ただし出力は変わる。下記） |
| 必須フィールドの追加 | **上げる** | 書いていない既存の IR が落ちる。`default` を付けても救えない（`required` の判定が先で、`default` は任意フィールドの欠落にしか効かない） |
| フィールドの削除・改名 | **上げる** | 消した側のキーが「未知のキー」として落ちる |
| 型の変更 | **上げる** | 値の形が変わる |
| `derived` の増減 | **上げる** | 入力だったフィールドを導出にすると、そのキーを書いていた IR が「自動計算です。入力から外してください」で落ちる。逆向きも値の出どころが変わる |
| 制約の強化（`max_length` を縮める、`pattern` を足す、`min_items` を増やす） | **上げる** | 通っていたものが落ちうる |
| `enum` の選択肢の削除 | **上げる** | 同上 |

補足が3つある。

- **軸は「検証を通るか」であって「出力が同じか」ではない。** 任意フィールドへの `default` 追加や `template.tex.j2` の修正は PDF の中身を変えるが、版は上げない。体裁は `schema_version` が版付けする対象ではない（charter §10 の「パッケージ ≠ テンプレート」）
- **制約の強化は「落ちうる」であって「必ず落ちる」ではない。** 手元の IR が全部通ることを確かめられる場合でも上げる側に倒す。パッケージ作者が既存の IR を全部把握できる保証が無いため
- **古い版を受け付け続ける仕組み（複数版の併存）は持たない。** 版が上がったら IR を書き直す。必要になった時点で別途決める

`document` 型の節（`sections`）の増減もこの軸で決まる（[issue #21](https://github.com/NPCdotcom/EnTeX/issues/21)）。任意の節を足すのは上げない、必須の節を足すのは上げる、になる。


## 7. 語彙に入れなかったもの

必要になる可能性はあるが、月次報告書 1 本の時点では入れない。**2 つ目の文書種で再判定する**（charter §11 着手順 3）。

| 候補 | 想定用途 | 入れない理由 |
|---|---|---|
| `time` / `time_range` | 開催時刻（14:00–16:00） | 月次報告書の活動実績に時刻欄があるか未確認。要るなら `text` で逃げずに型を足す |
| `number`（小数） | 活動時間 2.5h、率 | 題材に無い。金額を小数にしないため、あえて無い方が安全 |
| `year` / 年度 | 決算書・予算書（学生団体の会計） | 月次報告書には無い。`integer` + `minimum` で足りる可能性もある |
| `url` / `email` / `phone` | 連絡先 | 題材に無い。入れるなら `text` + `pattern` で足りるか先に検討 |
| `image` / `attachment` | 活動写真 | **アーキテクチャに効く**（アップロード・保存・参照）。IR に入れるならファイル参照になる。charter の非目的ではないが、初期版の範囲外として扱う |
| `person` | 役職 + 氏名 | `object` で表せる。専用型にする利得が無い |

> **2026-09-12 注記**: 最初の文書種を部会ログのフォーマット化に差し替えたことで（ADR-0001）、`time` / `time_range`（開催時刻・開始〜終了）は再判定の優先度が上がる可能性がある（部会ログは会議の開催時刻を記録する運用が一般的なため）。ユーザー提示の実物様式を見て、2つ目の文書種を待たずに前倒しで判断してよいか検討する。

## 8. `schema.json` の書き方（決定: 案1）

> **決定（2026-09-12、[issue #23](https://github.com/NPCdotcom/EnTeX/issues/23)）: 案1 を正本とする。案2 は採らず、案1 からの生成物としても出さない。**

型の語彙をファイルにどう書くか、次の 2 案を並べていた。

- **案 1: EnTeX 独自の簡潔な形式。** `{ "type": "money", "label": "金額", "minimum": 0 }`。ローダが pydantic モデルに変換する。フォーム自動生成が型の意味（月選択か日付選択か）を直接読める
- **案 2: JSON Schema（draft 2020-12）そのまま。** `money` は `{ "type": "integer" }` になり、意味は `format` か拡張キーワード（`x-entex-type`）で補う。既存のバリデータやフォーム生成ライブラリ（react-jsonschema-form 等）が使える

案1を採る理由は当初の推奨と同じで、型の意味を落とさないことと、語彙が閉じていて変換が機械的なことである。加えて、**着手順 1・2 の実装がすでに案1で動いている**。

| 実装 | 案1であることの根拠 |
|---|---|
| [`src/entex/ir/schema.py`](../../../src/entex/ir/schema.py) | 冒頭の docstring が「doc-package の `schema.json`（案1 形式）を表す pydantic モデル」と書いている。`FieldType` は §1 の 11 型そのもの、`FieldDef` の属性は §3 の表そのもの |
| [`packages/circle-monthly-report/schema.json`](../../../packages/circle-monthly-report/schema.json) | 案1の形で書かれている。当初は「仮に」だったが、これが唯一の実例になった |
| CLI・API・テスト | この読み込みの上に乗っている。`GET /v1/doc-types` が返す `schema_version` も `Schema` モデルの値 |

### 案2を落とす

当初の推奨は「案1を正本にし、案2を生成物として出す」だったが、**生成物としても出さない**。

生成側は実装されていない。`make schemas` が出しているのは `schemas/ir/envelope.schema.json`（封筒）と `schemas/api/`（OpenAPI）だけで、パッケージの `schema.json` から JSON Schema への変換は無い。使う当てのある外部ツールも今は無く、生成物を置けば「元とズレていないか」を見るテストの保守だけが残る。

要ると分かるのは着手順 4（フォーム UI）で外部のフォーム生成ライブラリを使うと決めたときだが、現状の想定ではフォームは `schema.json` を直接読む。型の意味が直接取れる方が都合がよい、というのが案1を採った理由そのものである。**必要になった時点で足す。** 変換が機械的であることは変わらないので、後から足す難度は今と変わらない。

## Facts

- charter §4・§10 により IR は見た目を含まない。型に表示形式を入れない根拠はここ
- charter §8 により renderer は IR の出どころを知らない。§2.2 で記法つき文字列を renderer に渡さない根拠はここ
- 円に小数単位は無い（`money` を integer にする根拠）
- 着手順は CLI → API → 2 つ目の文書種（charter §11）。§7・§8 の「2 つ目で再判定」はこれに従う

## Assumptions

- サークルの月次報告書に、時刻・小数・写真の欄が無い（**実物を確認していない**）
- 活動実績・会計明細の行数は 1 ページに収まる程度（数十行以下）
- 導出値は加算とフィルタで足りる（掛け算・割合は要らない）
- 月次報告書の項目構成（団体情報・会員数・活動実績・会計・次月予定・特記事項）は一般的なサークル報告書の形に沿っている（**実物未確認**。`packages/circle-monthly-report/` はこの仮定で書いた）
- `rich_text` の入れ子箇条書き・行内装飾は要らない

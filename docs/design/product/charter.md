## 2. 背景・動機

実務上の動機:

- ExcelやWordなどの汎用性の高いツールは情報の堅牢性に問題が生じやすいため、あらかじめこちらで決めたシステムに則って自動生成するソフトが欲しいと思ったため。
- TeXをより誰でも扱いやすいソフトウェアとして使用できるようにしたい。

その背景にある考え:

- **体裁が内容を侵食する。** WordやExcelでは、書き手が文書を作るたびにレイアウトを組み直している。本来は内容に向けるべき労力が見た目の調整に吸われ、しかもその努力は次回に引き継がれない。内容と体裁の分離はTeXが既に解決した問題であるにもかかわらず、習得コストのせいで一部の人にしか届いていない。
- **同じ種類の文書は同じ形をしているべきである。** 書式が人によって違う文書群は、読み手に毎回読み方を組み直すことを強いる。体裁の統一は美観の問題ではなく、読み手の負担と読み違いの問題である。
- **手作業には再現性がない。** 同じ手順で作ったはずのExcel文書が同じ結果になる保証はない。生成を機械に任せるということは、体裁を決定的なものにするということである。

まとめ: 目的は新しい組版技術を作ることではなく、**既にある組版の恩恵を、それを書けない人に渡すこと**にある。

> NPC: 動機としてはこじんまりとした思想的な部分もしっかり出した方が良い。
>
> Aster: 3点足した。元の2点は実務上の動機として残し、その下に置いてある。過不足があれば直してほしい。

## 4. 目的・非目的

| 目的（やること） | 非目的（やらないこと） |
|------------------|------------------------|
| 一度書式を定義すれば、以後は入力するだけで同じ体裁のPDFが出る | 自由レイアウトの編集（WYSIWYG）はやらない |
| 利用者はTeXを一切見ない。エラーメッセージも含めて見せない | 任意のDBへの直接接続は初期版ではやらない（§8の`data-import`として分離） |
| 同じ入力からは常に同じPDFが出る（生成が決定的である） | 承認フロー・電子署名・共同編集はやらない |
| 文書の種類を、本体のコードを変えずに増やせる | Word/Excelファイルの読み込み・変換はやらない |

4つ目が設計上の核である。これを守れているかどうかは、文書種を2つ作った時点で判定できる（§6）。

| 観点 | 想定 |

### 5.1 入力形式 — front matter + Markdown本文

型のある値はfront matterに置き、本文はMarkdownで書く。回次の見出し（`7/10(金) 第11回部会（通算47回）`）は入力に書かない。テンプレートがfront matterから組み立て、曜日は開催日から導く。

次は`club-meeting-log`の例である。ただし**このfront matterを人間が書くとは限らない**。部会ログでは`data-import`が埋める（§5.2）。

```markdown
---
doc_type: club-meeting-log
schema_version: 1
organization: 情報技術研究部
meeting_date: 2026-07-10
session_no_total: 47
---

## 活動報告
...
## アナウンス
...
```

本文は素のMarkdownではなく、**節の構成を文書種のパッケージが宣言する**（`schema.json`の`document`型。節の宣言・持てるblock・属性の詳細は[ir-type-vocabulary.md §2.8](../elements/ir-type-vocabulary.md#28-document節に分かれた本文)に置く）。素の変換にすると節を自由に増やせてしまい、§2・§6の「同じ文書種は同じ形」が消えるため。実物に合わせて3点決めた。

- **節の見出しレベルは検証しない。** `#`でも`##`でも同じ節として受け、正規化する。利用者に見出しレベルを意識させるのは§4「利用者はTeXを一切見ない」の精神に反する。一方、宣言した節の順序は固定する
- **臨時の節は許す**（宣言節の後ろに回す）。実物に少数ある以上、禁止すると過去ログの大半が通らない
- **節の中の下位見出し**（`### イベント名`）**は自由。** ここが実質の内容で、毎回変わる

これでPandoc（素のMarkdown → PDF）との違いがはっきりする（§9）。EnTeXは「節の構成が文書種によって決まっているMarkdown → PDF」である。Markdownを解釈するのは`renderer`ではなく入力側（§8の`data-import`）で、`renderer`にはblockしか届かない。

### 5.2 メタ情報の入り口 — 部会ログはNotionのプロパティから取る

§5.1のfront matterを、部会ログでは**人間が1文字も書かない**。実物から読み取れる書き方がそれを許さないためである。

- 作成日が開催日より前（第47回は作成7/3・開催7/10・最終更新7/10 15:40）。骨組みを事前に作り、会議中から直後に埋めている
- 部長の懺悔・会計長の懺悔が一人称で並んでおり、**書き手が複数いる**
- 画像101枚はすべてスクリーンショットの貼り付けである

複数人が会議中に画像を貼りながらNotionに書く、というのが実態で、その最中に`session_no_total: 47`は書けない。したがって**入力はNotionのエクスポートを第一の経路にし、メタ情報はページのプロパティから取る**。手入力はゼロにする。

| 項目 | 取り方 |
|---|---|
| 開催日 | 既存のNotionプロパティ`開催日`（実物47本すべてにある） |
| 通算回次 | NotionのIDプロパティ（自動採番） |
| 年度 | `開催日`からの数式プロパティ（4月始まり） |
| 曜日 | 入力しない。`meeting_date`から`ja_date`フィルタで出す |
| 団体名 | パッケージ側の定数。入力しない |

**今年度の回次は持たない。** 実物は「第11回部会（通算47回）」と両方書いていたが、両方あると片方が古くなる。実際に`10/16 第28回`と`10/16 第29回`、`11/06 第30回`と`11/06 第31回`という重複が起きている（§3の(4)）。通算だけにして自動採番から取れば、人間が数える箇所そのものが消える。

Notionのプロパティ名（`開催日`）は`src/entex/`に持ち込まない。doc-package側のフィールド属性に置く。

```json
"meeting_date": {
  "type": "date",
  "label": "開催日",
  "source": { "notion_property": "開催日" }
}
```

インポータは`source`を読むだけで、プロパティ名そのものを知らない。§8の境界がそのまま保たれる。属性`source`の正本は[ir-type-vocabulary.md](../elements/ir-type-vocabulary.md) §3に置く。

書式を決めても、使われなければ何も揃わない。**継続して使われることを、体裁の厳密さより優先する。** 検証も寛容にし、止めるのは`開催日`が無いときだけにする。同じ形になることは、入力を縛るのではなく出力側で揃えて達成する（§5.1の3つの規則と、空の節をPDFから落とすこと）。

> Aster（2026/9/12、[issue #20](https://github.com/NPCdotcom/EnTeX/issues/20)）: §5.1を書いた時点ではfront matterを人間が書く前提だったが、実物の作成日時と書き手の複数性を見て改めた。§3の(4)に「回次が壊れている」と記録しながら、その原因である二重の回次を入力例が書かせていたので、そこも直した。front matter + Markdownという形式自体は`markdown`アダプタ（§8）として残るので、§5.1は生きている。

## 6. 成功の目安

成功:

- TeXを知らない人が、口頭の説明なしで文書（部会ログ）を1本PDFにできる
- 同じ文書種で別々の人が作ったPDFが、**体裁上**同一になる。ここでの「体裁上同一」は次の水準を指す
  - 宣言した節の有無と順序が一致する
  - メタ情報（回次・開催日・団体名など）の書式が一致する。§3の回次見出しの揺れが0になる
  - 見出しの階層（節・下位見出し）とblock（段落・箇条書き・引用・画像）の見え方が一致する
  - 本文の内容と長さは毎回違うので、行数・ページ数の差は「体裁の差」に含めない
- **文書種を1つ増やすのに、本体のコードを1行も変えずに済む**
- 生成が10秒以内に終わる

失敗・避けたい状態:

- 文書種を増やすたびに本体のコードを直している状態
- 利用者の画面にLaTeXのエラーログがそのまま出ている状態
- 「Wordでやった方が速い」と言われる状態
- DB接続・認証・権限管理に着手して、PDFが1枚も出ないまま止まっている状態

3つ目の成功条件は願望ではなく設計の合否判定として使う。**実物に基づく**文書種が2つになった時点で判定する。`packages/circle-monthly-report/`は実物に基づかないため判定の材料にはならず、1つ目は`club-meeting-log`、判定は実物に基づく2つ目が出てから行う（issue #14）。判定する側と本体を書いた側が同じだと判定が機能しないため、`packages/`と`src/entex/`の担当を分ける（分担の正本は[docs/TEAM.md](../../TEAM.md)に書く）。

> Aster（2026/9/12、issue #14）: 2つ目の成功条件を「まったく同一」から水準つきに書き直した。月次報告書のような欄が並ぶ書類なら別々の人のPDFがまったく同一になり得るが、議事録は内容が毎回違うので文字どおりの同一にはならない。何が揃えば「体裁上同一」と言うかを書いておかないと、判定のたびに解釈が揺れる。

> 注: `document`型の追加・Markdown取り込み・blockのTeX展開は`src/entex/`側の変更になるが、これは型の語彙を広げる変更であって文書種を増やす変更ではない。3つ目の成功条件が禁じているのは後者である。

## 7. 制約・前提

| 種類 | 内容 |
|------|------|
| 技術・言語・ランタイム | Python（FastAPI + pydantic + Jinja2）。フロントはReact。C++は使わない（§11） |
| 組版エンジン | LuaLaTeX + luatexja。日本語のためupLaTeX + dvipdfmxは採らない |
| プラットフォーム | 開発: WSL2 Ubuntu + Docker（単一コンテナ） / 利用: ブラウザ |
| 期間・マイルストーン感 | 未定。ただし着手順は決めてある（§11の下） |
| 法務・ライセンス・公開範囲 | リポジトリは公開。TeX Liveを再配布しないため同梱ライセンスの問題は生じない |
| 依存する外部サービス | 初期版はなし。配置先のPaaSのみ（候補: Fly.io / Cloud Run、§11） |

補足として、**開発コードはWSL2側のファイルシステムに置く**。Windows側のディレクトリをバインドマウントするとファイルI/Oが大幅に遅くなり、TeXは中間ファイルを大量に書くためコンパイル時間に直接効いてくる。

## 8. 主要要素（名前だけ · のち H1）

- `doc-package` — 文書種1つ分の定義。スキーマ・テンプレート・スタイルの束。本文主体の文書種では、節の構成もここで宣言する（§5.1）
- `ir-schema` — 文書の中身を見た目抜きで表す中間表現と、その検証。本文は節とblockの構造（`document`型）で持つ
- `form-ui` — スキーマから自動生成される入力画面。着手順4
- `renderer` — 中間表現とパッケージから .tex を組み立て、PDFにする
- `job-runner` — 生成の実行、ログ、成果物の管理
- `data-import` — フォーム以外の入力から中間表現を作る。**最初の入力経路はNotionのエクスポートの取り込み（`notion-export`）**で、汎用の front matter + Markdown（`markdown`）はその後（着手順3、下のアダプタ表）。CSVは着手順5、DBはさらに後。`renderer` からは分離したまま

`renderer` は中間表現がどこから来たかを知らない、という境界を守る。Markdownの解釈はこの境界の外側（`data-import`）で行い、`renderer` には節とblockに変換済みの中間表現しか届かない。これを守っている限り、入力経路（Markdown・フォーム・CSV・DB）を足しても `renderer` と `doc-package` に手を入れずに済む。

`data-import` は入力の種類ごとにアダプタを持つ。当面は2本で、違いはメタ情報の読み取り方だけである。本文をblockに変換する部分は共通にできる。

| アダプタ | 入力 | 実装順 |
|---|---|---|
| `notion-export` | Notionのエクスポート（タイトル行 + プロパティ行 + 本文）。メタ情報はプロパティから取る（§5.2）。タイトル行は読まない | 先 |
| `markdown` | YAML front matter + 本文（§5.1）。他の文書種・他のソース向けの汎用形 | 後 |

どちらも出力は同じ形の中間表現で、`renderer` から見て区別がつかない。Notionを知るのは `notion-export` だけである。

> Aster（2026/9/12、issue #14）: `data-import` の「後回し」を外した。Markdown取り込みが最初の入力経路になるため。ただし「分離済み」は変えていない。Markdownを`renderer`が解釈すると`renderer`が記法を知ることになり、テンプレートが解釈するとTeX側にパーサを書くことになる。どちらも避け、入力側でblockへ変換する（ir-type-vocabulary.md §2.2で既に決めていた方針の適用）。

## 10. 用語・ドメインメモ（任意）

| 用語 | 仮の意味 |
|------|----------|
| 文書種（doc type） | 部会ログ・請求書など、書式が1つ決まっている文書のまとまり |
| パッケージ | 文書種1つ分の定義の全体。スキーマ・テンプレート・スタイルを含む |
| テンプレート | **要注意語**。ここではTeXの雛形ファイルだけを指す。定義全体はパッケージと呼び分ける |
| IR（中間表現） | 文書の中身を、見た目を含まない形で表したデータ |
| テンプレート作者 / 利用者 | 前者はTeXを書く役（当面は我々）、後者は入力するだけの役。権限も分ける |
| front matter | 入力ファイル冒頭の、型のある値の組（開催日・回次など）。IRのスカラー欄になる |
| 本文（`document`） | Markdownで書く部分。節とblockから成る。IRでは型`document`として持つ |
| 節（section） | 本文の大見出し1つ分（活動報告・アナウンスなど）。文書種が宣言し、順序と必須/任意を持つ |
| block | 本文の構成単位（段落・箇条書き・引用・リンク・画像）。`renderer`が受け取る最小単位で、Markdownの記法はここまでに解釈し終わっている |

「テンプレート」は2つの意味で使われて確実に混乱するため、先に決めておく。「テンプレートが未記入のまま残っている」（§3の`N/N(N) 第N回部会`）のように実物の中で出てくる「テンプレート」はNotionの雛形ページのことで、ここでの意味とは別である。

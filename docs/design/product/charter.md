## 1. 一行説明

TeXを知らない人が、フォームに入力するだけで、決められた書式どおりのPDFを崩さずに出力できるWebアプリケーション。

> NPC: これについても改変があるなら教えて。

## 2. 背景・動機

実務上の動機:

- ExcelやWordなどの汎用性の高いツールは情報の堅牢性に問題が生じやすいため、あらかじめこちらで決めたシステムに則って自動生成するソフトが欲しいと思ったため。
- TeXをより誰でも扱いやすいソフトウェアとして使用できるようにしたい。

その背景にある考え:

- **体裁が内容を侵食する。** WordやExcelでは、書き手が文書を作るたびにレイアウトを組み直している。本来は内容に向けるべき労力が見た目の調整に吸われ、しかもその努力は次回に引き継がれない。内容と体裁の分離はTeXが既に解決した問題であるにもかかわらず、習得コストのせいで一部の人にしか届いていない。
- **同じ種類の文書は同じ形をしているべきである。** 書式が人によって違う文書群は、読み手に毎回読み方を組み直すことを強いる。体裁の統一は美観の問題ではなく、読み手の負担と読み違いの問題である。
- **手作業には再現性がない。** 同じ手順で作ったはずのExcel文書が同じ結果になる保証はない。生成を機械に任せるということは、体裁を決定的なものにするということである。

まとめ: 目的は新しい組版技術を作ることではなく、**既にある組版の恩恵を、それを書けない人に渡すこと**にある。

>
> Aster: 3点足した。元の2点は実務上の動機として残し、その下に置いてある。過不足があれば直してほしい。

## 3. 誰のためのものか（利用者）

| 利用者 | 主な目的・状況 | 優先度（高/中/低） |
|--------|----------------|--------------------|
| 大学のサークルの運営者 | サークル内の部会（会議）のログを都度まとめており、担当者や回によって体裁がまちまちになる（詳細はissue #11を受けて追ってユーザーから提示・反映） | 高 |

| 会社の上司 | 業務書類が人によってフォーマットが違い過ぎるので見づらい | 中 |

- 承認フロー・電子署名が業務要件に含まれる組織 — 初期スコープ外（§4の非目的）

## 4. 目的・非目的

| 目的（やること） | 非目的（やらないこと） |
|------------------|------------------------|
| 一度書式を定義すれば、以後は入力するだけで同じ体裁のPDFが出る | 自由レイアウトの編集（WYSIWYG）はやらない |
| 利用者はTeXを一切見ない。エラーメッセージも含めて見せない | 任意のDBへの直接接続は初期版ではやらない（§8の`data-import`として分離） |
| 同じ入力からは常に同じPDFが出る（生成が決定的である） | 承認フロー・電子署名・共同編集はやらない |
| 文書の種類を、本体のコードを変えずに増やせる | Word/Excelファイルの読み込み・変換はやらない |

4つ目が設計上の核である。これを守れているかどうかは、文書種を2つ作った時点で判定できる（§6）。

## 5. 成果物のイメージ

| 観点 | 想定 |
|------|------|
| 利用者から見える形 | ブラウザで、文書種を選ぶ → フォームに入力 → プレビュー → PDFを保存、の3ステップ |
| 主な入出力 | 入力: フォームの値（将来はCSV、さらに後でDB） / 出力: PDF（および生成に使った .tex） |
| 「動いた」と言える最小状態（MVP） | 文書種1つ（サークルの部会ログのフォーマット化）で、フォーム入力からPDFのダウンロードまで通る。文書種の追加はまだ手作業でよい |

画面は3つを想定している。文書種の管理（我々のみ）、作成、生成履歴。

> NPC（2026/9/12、issue #11）: MVPの題材を「サークルの月次報告書」から「サークルの部会ログのフォーマット化」に差し替えた。理由と経緯は§3のAsterの追記・§11の決着済み・ADR-0001を参照。

## 6. 成功の目安

成功:

- TeXを知らない人が、口頭の説明なしで報告書を1本PDFにできる
- 同じ文書種で別々の人が作ったPDFが、体裁上まったく同一になる
- **文書種を1つ増やすのに、本体のコードを1行も変えずに済む**
- 生成が10秒以内に終わる

失敗・避けたい状態:

- 文書種を増やすたびに本体のコードを直している状態
- 利用者の画面にLaTeXのエラーログがそのまま出ている状態
- 「Wordでやった方が速い」と言われる状態
- DB接続・認証・権限管理に着手して、PDFが1枚も出ないまま止まっている状態

3つ目の成功条件は願望ではなく設計の合否判定として使う。文書種が2つになった時点で判定する。

## 7. 制約・前提

| 種類 | 内容 |
|------|------|
| 技術・言語・ランタイム | Python（FastAPI + pydantic + Jinja2）。フロントはReact。C++は使わない（§11） |
| 組版エンジン | LuaLaTeX + luatexja。日本語のためupLaTeX + dvipdfmxは採らない |
| プラットフォーム | 開発: WSL2 Ubuntu + Docker（単一コンテナ） / 利用: ブラウザ |
| 期間・マイルストーン感 | 未定。ただし着手順は決めてある（§11の下） |
| 法務・ライセンス・公開範囲 | リポジトリは公開。TeX Liveを再配布しないため同梱ライセンスの問題は生じない |
| 依存する外部サービス | 初期版はなし。配置先のPaaSのみ（候補: Fly.io / Cloud Run、§11） |

補足として、**開発コードはWSL2側のファイルシステムに置く**。Windows側のディレクトリをバインドマウントするとファイルI/Oが大幅に遅くなり、TeXは中間ファイルを大量に書くためコンパイル時間に直接効いてくる。

## 8. 主要要素（名前だけ · のち H1）

- `doc-package` — 文書種1つ分の定義。スキーマ・テンプレート・スタイルの束
- `ir-schema` — 文書の中身を見た目抜きで表す中間表現と、その検証
- `form-ui` — スキーマから自動生成される入力画面
- `renderer` — 中間表現とパッケージから .tex を組み立て、PDFにする
- `job-runner` — 生成の実行、ログ、成果物の管理
- `data-import` — CSVやDBから中間表現を作る。**分離済み・後回し**

`renderer` は中間表現がどこから来たかを知らない、という境界を守る。これを守っている限り、`data-import` を後から足しても `renderer` と `doc-package` に手を入れずに済む。

## 9. 参考・類似・差別化（任意）

| 参考・競合・類似 | 取りたい点 | 避けたい点 |
|------------------|------------|------------|
| Overleaf / LaTeXテンプレート集 | 組版品質、テンプレートを資産として扱う考え方 | TeXが書けることを前提にしている |

## 10. 用語・ドメインメモ（任意）

| 用語 | 仮の意味 |
|------|----------|
| 文書種（doc type） | 請求書・月次報告書など、書式が1つ決まっている文書のまとまり |
| パッケージ | 文書種1つ分の定義の全体。スキーマ・テンプレート・スタイルを含む |
| テンプレート | **要注意語**。ここではTeXの雛形ファイルだけを指す。定義全体はパッケージと呼び分ける |
| IR（中間表現） | 文書の中身を、見た目を含まない形で表したデータ |
| テンプレート作者 / 利用者 | 前者はTeXを書く役（当面は我々）、後者は入力するだけの役。権限も分ける |

「テンプレート」は2つの意味で使われて確実に混乱するため、先に決めておく。

決着済み:

- ~~実装形態と言語をどうするか~~ → 案B（Webアプリ・Python）を採用（2026/9/12）。退けた案は次の2つ。**案A: C++/Qtのデスクトップアプリ**は、C++が活きオフラインでも動くが、TeX Liveを同梱すると配布物が数GBになり、更新のたびに再配布が要る。§3の利用者に入れてもらうのは難しいと判断した。**案C: C++のコアエンジン + 薄いWeb層**は両立するが、2言語分の工数がかかるため見送った。案Bの代償として、C++を書く場面はなくなる。
- ~~最初の文書種の題材を何にするか（サークルの月次報告書を仮に置いている）~~ → **サークルの部会ログのフォーマット化**に差し替え（2026/9/12、[issue #11](https://github.com/NPCdotcom/EnTeX/issues/11)）。issue #11の実物確認作業の過程で、情報技術研究部には月次報告書を提出する運用自体が存在しないと判明したため。`renderer`・CLI・APIなど着手順1〜2で作った本体側の実装は文書種の中身に依存しない設計（charter §8）のため作り直しは不要で、影響は`packages/circle-monthly-report/`とその要求・要件ドキュメントに閉じる。経緯・判断は[ADR-0001](../../adr/0001-first-doc-type-pivot-to-meeting-log.md)に記録。具体的な様式はユーザー提示の情報を受けて確定する（上のOpen questions参照）。

着手順（各段で動くものが残る形にしてある）:

1. CLIで1本通す。`JSON → PDF`。ここでスタイル・テンプレート・TeXのエスケープ・latexmk呼び出しを固める
2. API化する。中間表現をPOSTするとPDFが返る
3. 文書種を2つに増やす。**ここでパッケージ構造の妥当性が判明するので、2つ目を作るまで先へ進まない**
4. UIを作る。スキーマからのフォーム自動生成、生成履歴、ジョブ化
5. CSV一括生成（1行1文書）

## Facts / Assumptions

**Facts**（確定している事実）:

- 共同者は2名（NPC, Aster）
- 案B（Webアプリ・Python・ブラウザ配布）を採用した（2026/9/12）
- 主対象は日本語の文書である
- 出力はLaTeXを経由したPDFである
- 情報技術研究部には月次報告書を学生課へ提出する運用自体が存在しない（issue #11、2026/9/12判明）。これによりMVPの題材は「サークルの部会ログのフォーマット化」に差し替えた（ADR-0001）

**Assumptions**（仮定・まだ検証していないこと）:

- 想定利用者が実際に型崩れに困っている。**サークル以外にはヒアリングしていない**。特に月次報告書についてはこの仮定自体が誤りだったと判明したため、部会ログについても同様に検証済みではない
- 利用者はTeXを一切書きたくない。書式の微調整を求める声は出ない
- 必要な文書種は数種類で足り、数十種類には膨らまない
- テンプレートの作成を我々が引き受けられる量に収まる
- 部会ログの具体的な様式（頻度・欄構成など）はユーザーから追って提示される。それまでは`schema.json`・`template.tex.j2`の詳細設計に着手しない

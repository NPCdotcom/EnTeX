# 要求定義 — サークル月次活動報告書

## 背景

charter §5 の MVP に定めた最初の文書種。大学サークルが学生課へ毎月提出する活動報告書を題材にする。理由は charter §3 の Aster 提案どおり: 我々自身が当事者で実物の報告書が手に入り、使ってもらって確かめるのが最も安いため。

現在の到達点（H1/scaffold）:

- IR の型語彙は確定（[ir-type-vocabulary.md](../../design/elements/ir-type-vocabulary.md)）
- `packages/circle-monthly-report/` に `schema.json`（案1・仮）と IR 例 12 件（valid 6 / invalid 6）が存在
- `template.tex.j2` とスタイルは未着手（着手順1で書く。charter §11）

この要求は、上記の scaffold を「なぜこの形にしたか」という利用者側の要求として言語化し、P2 の検証可能な要件、P3 の renderer 基本設計につなげるためのもの。

## ステークホルダー / 利用者

| 役割 | 内容 | 優先度 |
|------|------|--------|
| 大学サークルの運営者（代表者・作成者） | 報告書を作成し提出する当事者。フォーム入力からPDFダウンロードまでを行う | 高（charter §3 最優先ターゲット） |
| 学生課 | 報告書の受け取り手。体裁が毎回同一であることを期待する間接的利用者 | 中（要求の受益者だが直接操作しない） |
| テンプレート作者（当面は我々） | `schema.json` / `template.tex.j2` を書き、実物の様式に合わせて直す役 | 高（P1時点では我々自身） |

対象外（charter §3 非利用者に準拠）: 既にLaTeXを書ける人、一点物の文書を作る人、承認フロー・電子署名が必要な組織。

## 要求一覧

| ID | 要求 | 優先度 |
|----|------|--------|
| R1 | 同じ入力なら常に同じ体裁のPDFが出る（生成が決定的） | must |
| R2 | 利用者はTeXを一切見ない。検証エラー・生成失敗のメッセージも日本語で、TeXの語を含まない | must |
| R3 | 入力は IR（JSON）1本。出力はPDF（および生成に使った `.tex`） | must |
| R4 | 会計の合計・残高・活動回数などの集計値は自動計算する。入力には含めさせない（`derived` キーを入力に含めたら拒否） | must |
| R5 | 検証エラーは見つかった分をまとめて返す。ただし封筒（`doc_type` / `schema_version`）の不一致は中身を見る前に止める | must |
| R6 | `& % $ # _ { } ~ ^ \ < >` や `'` を含む自由記述（団体名・活動概要など）を、TeXを壊さず安全に出力できる | must |
| R7 | 生成は10秒以内に終わる（charter §6 成功の目安） | should |
| R8 | 会員数・活動実績・会計明細のように0件（活動休止月・経理なし月）もそのまま扱える | must |
| R9 | 残高が負（赤字）になる月も正しく扱える | must |
| R10 | 文書種を1つ増やす際、`src/entex/` 本体のコードを変更せずに済む（charter §4 設計の核。この要求単体では検証できず、2文書種目で判定） | must（判定は2文書種目） |

## 成功のイメージ（非技術）

サークルの代表者・作成者が、月次の活動・会計データをIR（当面はJSON、将来はフォーム）として用意すると、コマンド一つ（将来はボタン一つ）で学生課にそのまま提出できるPDFが出る。会計の合計や残高は自分で計算し直す必要がなく、毎月・誰が作っても同じ見た目になる。入力を間違えても、TeXのエラーではなく「団体名は1行で入力してください」のような日本語のメッセージで気づける。

## エージェント提案（選択肢・推奨）

実物の学生課様式（Word版）がまだ手元にない中で、P1〜P4を進めてよいかという論点。

| 選択肢 | メリット | デメリット |
|--------|----------|------------|
| A: 仮の `schema.json` / 仮レイアウトの `template.tex.j2` で先に renderer 本体を作る。実物入手後にフィールド構成とレイアウトだけ直す | renderer のロジック（検証・导出値計算・エスケープ・latexmk呼び出し）は実物の様式に依存しないため、待たずに着手できる。着手順1の「動くものを残す」方針（charter §11）に合う | 実物と乖離したフィールドで作業する手戻りリスク。`schema.json` のフィールド名・行数上限は後で変わる可能性が高い |
| B: 実物の入手を待ってから着手する | 手戻りが少ない | いつ手に入るか未定（Open questions）。charter §6 の失敗パターン「PDFが1枚も出ないまま止まっている状態」に近づく |

**推奨**: A。renderer のコアロジックは `schema.json` の中身に依存しない設計（`renderer` は IR の出どころもパッケージの中身の詳細も知らない、という charter §8 の境界）なので、実物待ちで全体を止める理由がない。フィールド構成・レイアウトの手戻りは `doc-package` 側だけに閉じる想定。

## Facts / Assumptions

**Facts**（確定している事実）:

- 最初の文書種はサークル月次活動報告書（charter §5 MVP）
- IR の型語彙は11型で確定済み（ir-type-vocabulary.md）
- `packages/circle-monthly-report/` に schema.json と IR 例12件が存在する

**Assumptions**（仮定・まだ検証していないこと。ir-type-vocabulary.md および packages/circle-monthly-report/README.md の記載を継承）:

- 学生課の実際の様式（項目名・欄の順序・行数）は未確認。現在の `schema.json` は一般的なサークル報告書の形に沿った仮定
- `activities` 上限10行・`finance` 上限20行はA4 1枚に収まる見込みで置いた仮の数値
- `student_id` の形式 `^[A-Z0-9]+$` は仮
- サークル以外の利用者（学生団体の会計担当・会社の上司など）へのヒアリングは未実施

## Open questions

- 実物のWord版報告書をいつ入手できるか（未確認・仮定の解消に必要）
- `schema.json` の書式（案1のコンパクト形式 vs JSON Schema生成）は2文書種目まで判断を保留してよいか（ir-type-vocabulary.md 既定の合意事項）
- 学生課への提出以外の用途（サークル内保管・引き継ぎ資料としての利用）を要件に含めるか

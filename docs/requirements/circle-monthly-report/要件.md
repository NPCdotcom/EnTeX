# 要件定義 — サークル月次活動報告書

> **2026-09-12 方針変更（[issue #11](https://github.com/NPCdotcom/EnTeX/issues/11) / [ADR-0001](../../adr/0001-first-doc-type-pivot-to-meeting-log.md)）**
> 親の要求（[要求.md](./要求.md)）が前提にしていた運用自体が実在しないと判明したため、最初の文書種はサークル内の**部会ログのフォーマット化**に差し替えた。以下は参考資料。FR1–FR8・NFR1–2（封筒検証・型検証・導出値計算・エスケープ・latexmk呼び出し・CLI・10秒以内・決定性）は文書種の中身に依存しない汎用要件として引き続き有効であり、新しい文書種の要件でも踏襲する見込み。

親: [要求.md](./要求.md)

## スコープ

### In scope

- IR（`packages/circle-monthly-report/schema.json` 案1準拠）の読み込みと検証
- 封筒（`doc_type` / `schema_version`）の検証
- 導出値（`activity_count` / `participants_total` / `income_total` / `expense_total` / `balance`）の生成時計算（ir-type-vocabulary.md §4 決定A）
- TeX特殊文字のエスケープ
- `template.tex.j2` によるPDF生成（実物の学生課様式入手前は仮レイアウトで進める。要求.md エージェント提案A）
- CLI `entex render <json>` から一連の処理を実行（charter §11 着手順1）
- 検証・生成失敗時の日本語エラーメッセージ化（TeXログを利用者に出さない。AGENTS.md）

### Out of scope（この要件では扱わない）

- API化（着手順2）
- 文書種2つ目以降・パッケージ構造の妥当性判定（着手順3）
- `form-ui`（フォーム自動生成、着手順4）
- `job-runner`（生成履歴・ジョブ化、着手順4）
- `data-import`（CSV一括生成、着手順5）
- 認証・権限管理
- `packages/circle-monthly-report/schema.json` のフィールド構成そのものの最終確定（実物のWord版報告書入手待ち。要求.md Open questions）

## 機能要件

| ID | 要件 | 検証方法 |
|----|------|----------|
| FR1 | 封筒（`doc_type` / `schema_version`）を中身より先に検証する。不一致なら日本語エラーで即座に止め、中身のエラーは報告しない | `examples/invalid/06-envelope-mismatch.json` を入力し、封筒エラー1件のみが返ることを確認するテスト |
| FR2 | 封筒が正しい場合、`content` を `schema.json` の11型（ir-type-vocabulary.md §1）に従って検証する。エラーは見つかった分を1回でまとめて返す | `examples/invalid/03-unknown-enum-and-negative-amount.json`（2件のエラーを含む）で、両方のエラーが1回の実行で返ることを確認するテスト |
| FR3 | `derived: true` のフィールドのキーが入力 `content` に含まれていたら拒否する | `examples/invalid/01-derived-key-in-input.json` でテスト |
| FR4 | 検証を通った IR について、`schema.json` の `expr`（`sum` / `count` / `add` / `sub`、`where`）に従って導出値を計算する。宣言順に評価し、循環参照は検証で拒否する | `examples/valid/01-typical.json`・`03-deficit.json`・`04-max-rows.json`・`05-fiscal-year-start.json` で、`packages/circle-monthly-report/README.md` に記載の期待値（例: 01は活動5回・延べ77人・残高19,400）と一致することを確認するテスト |
| FR5 | `text` / `rich_text` の文字列値は、`& % $ # _ { } ~ ^ \ < > '` を含めTeXコンパイルを壊さない形にエスケープしてから `.tex` へ渡す | `examples/valid/06-tex-special-chars.json` で、生成された `.tex` に未エスケープの制御文字が残らないことを確認するテスト |
| FR6 | 検証済みIRと doc-package の `template.tex.j2` から `.tex` を組み立て、`latexmk -lualatex` でPDFを生成する | `examples/valid/01-typical.json` からPDFが生成されること（Docker環境、`make docker-test` 相当） |
| FR7 | `latexmk` 失敗時、利用者向けにはTeXログを含まない日本語の要約エラーを返し、原文はサーバ側ログにのみ残す | 意図的に壊れた `template.tex.j2` で失敗させ、CLI標準出力・戻り値にTeX語彙（例: `! LaTeX Error`）が含まれないことを確認するテスト |
| FR8 | `entex render <json>` コマンドでFR1–FR6を一連で実行できる | `entex render examples/valid/01-typical.json` が終了コード0でPDFパスを出力することを確認する統合テスト |

## 非機能要件（該当時）

| ID | 要件 | 検証方法 |
|----|------|----------|
| NFR1 | 生成は10秒以内に終わる（charter §6 成功の目安） | `01-typical.json` の生成時間を計測する目安テスト（厳密なSLA試験ではなく、大幅な劣化の検知が目的） |
| NFR2 | 同じ入力からは常に同じPDFが出る（生成が決定的。charter §4） | 同じIRを2回生成し、出力される `.tex`（生成時刻等のメタデータを除く）が一致することを確認するテスト |

## エージェント提案（実装方針のたたき）

**推奨**: 案2。責務ごとに分割することで、charter §8 の境界（`renderer` は doc-package の中身を知っていてよいが IR の出どころは知らない）をコードの構造に反映でき、2文書種目でパッケージ構造の妥当性を判定する際（charter §11 手順3）に doc-package 非依存の部分とパッケージごとに変わる部分の境目が確認しやすくなる。

| 案 | 概要 | 向く状況 |
|----|------|----------|
| 1 | `renderer.py` に読み込み・検証・導出計算・エスケープ・テンプレ組み立て・latexmk呼び出しを1本で書く | 最速で1本通すことだけが目的で、構造の検証は後回しでよい場合 |
| 2 | 責務ごとに分割: `ir/loader.py`（schema.json読み込み・pydanticモデル化・封筒/型検証）、`ir/derive.py`（`expr` 評価）、`tex/escape.py`（エスケープ）、`renderer.py`（テンプレ組み立て・latexmk呼び出し）、`cli.py` に `render` コマンドを追加 | FR1–FR8 のうち検証・導出計算（doc-package非依存に近い部分）とテンプレ組み立て（doc-package依存部分）を分けて2文書種目の判定材料にしたい場合 |

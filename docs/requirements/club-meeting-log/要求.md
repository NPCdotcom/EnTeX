# 要求定義 — サークル部会ログ

最初の文書種（charter §5 の MVP、`club-meeting-log`）。情報技術研究部が部会ごとに Notion で書いている記録を、同じ体裁の PDF にする。

[ADR-0001](../../adr/0001-first-doc-type-pivot-to-meeting-log.md) が「様式が判明するまで P1 からやり直す」としていた分である。差し替え前の [circle-monthly-report の要求](../circle-monthly-report/要求.md) は参考資料として残す。

## 背景

前の題材（サークル月次活動報告書）は、**運用そのものが実在しなかった**（[issue #11](https://github.com/NPCdotcom/EnTeX/issues/11)、ADR-0001）。実物が全数手に入る題材として部会ログに差し替え、[issue #14](https://github.com/NPCdotcom/EnTeX/issues/14) で 2024/5〜2026/7 の47本を全数集計した。この要求はその実測だけを材料にしており、**仮定に基づく項目は置いていない**。ここが前の要求との最大の違いである。

実測の要点（charter §3 に反映済み）:

| 観点 | 実測 |
|---|---|
| 本数・期間 | 47本、2024/5〜2026/7。頻度は週1回程度 |
| メタ情報 | Notion のページプロパティ3つ（作成日・最終更新日時・開催日）。`開催日` は47本すべてにある |
| 節 | アナウンス 44 / 活動報告 34 / 次回予告 4。ほかは臨時の節（幹部自己紹介3・リマインド3・部費回収2 など） |
| block | 箇条書き 721・引用 151・インラインリンク 103・画像 101・コード 6。**表は0件** |
| 回次の見出し | 漢数字と算用数字、曜日の有無、括弧の全角半角、通算と今年度の順序、H1/H2 がすべて揺れている。未記入のテンプレート（`N/N(N) 第N回部会`）や同日重複もある |

現在の到達点:

- IR の型語彙は確定し、本文用の `document` 型も設計が済んでいる（[ir-type-vocabulary.md §2.8](../../design/elements/ir-type-vocabulary.md#28-document節に分かれた本文)、[issue #21](https://github.com/NPCdotcom/EnTeX/issues/21)）。実装は[issue #30](https://github.com/NPCdotcom/EnTeX/issues/30)（PR #32）で済んだ
- `schema.json` の形式は案1で確定（同 §8、[issue #23](https://github.com/NPCdotcom/EnTeX/issues/23)）
- 入力の第一の経路は Notion のエクスポートで、メタ情報はページのプロパティから取る（charter §5.2、[issue #20](https://github.com/NPCdotcom/EnTeX/issues/20)）

## ステークホルダー / 利用者

| 役割 | 内容 | 優先度 |
|------|------|--------|
| 部会ログを書く部員 | 会議中から直後に Notion へ書く。**複数人が同じページに書く**（部長の懺悔・会計長の懺悔が一人称で並ぶ）。書式を意識せずに書けることが最優先 | 高 |
| 部会ログを読む部員 | 欠席した回を後から追う人、過去の決定を探す人。回次・開催日・節の並びが揃っていることを期待する | 高 |
| 部の運営を引き継ぐ側 | 年度をまたいで同じ形の記録が残ることを期待する。回次の揺れは引き継ぎの妨げになる | 中 |
| テンプレート作者（当面は我々） | `schema.json` / `template.tex.j2` を書き、実物に合わせて直す役 | 高 |

対象外は charter §3 の非利用者に準拠する。加えて、**この文書種には承認・確認のフローが無い**（実測。charter §3 の Aster 追記）ので、提出物としての要求は持たない。

## 要求一覧

| ID | 要求 | 優先度 | 出どころ |
|----|------|--------|---------|
| R1 | 回次の見出しを**人が書かない**。開催日と通算回次からテンプレートが組み立てる | must | 実測の揺れ（charter §3 (4)）。これが題材を選んだ理由そのもの |
| R2 | 節の並びは `schema.json` の宣言順に固定する。入力に書かれた順序は見ない | must | charter §5.1 |
| R3 | 宣言していない臨時の節も**落とさずに出す**（宣言節の後ろに回す） | must | 臨時の節が実測で少数ある。禁止すると過去ログの大半が通らない |
| R4 | 節の見出しレベルの揺れ（`#` / `##`）を正規化して受ける。利用者に見出しレベルを意識させない | must | charter §4「利用者は TeX を一切見ない」の精神。実測で H1/H2 が混在 |
| R5 | メタ情報（開催日・通算回次・年度）を**人が1文字も書かない**。Notion のページプロパティから取る | must | charter §5.2。会議中に書ける情報ではない |
| R6 | 検証は寛容にする。**止めるのは開催日が無いときだけ**にする | must | charter §5.2。継続して使われることを体裁の厳密さより優先する |
| R7 | 空の節は PDF に出さない | should | 次回予告が47本中4本にしかない。空の見出しが並ぶと体裁が崩れる |
| R8 | 本文中のリンクは、文言と URL の**両方**を保つ | must | インラインリンク103件。資料・フォームの所在なので、どちらが落ちても使えない |
| R9 | 画像を本文中に置ける | must（MVP の次） | 画像101枚。直近の回ほど画像が主役で、最新の第47回は本文がほぼ画像だけ |
| R10 | `& % $ # _ { } ~ ^ \ < >` を含む本文を TeX を壊さず出力できる。コードブロックだけは書いたとおりに出す | must | コードブロック6件。charter §4 |
| R11 | 同じ入力なら常に同じ PDF が出る。生成は10秒以内 | must / should | charter §6 |
| R12 | この文書種を足すのに `src/entex/` を1行も変えずに済む | must（判定は着手順3b） | charter §4・§6。ただし型語彙を広げる変更は「文書種を増やす変更」に当たらない（charter §6 の注記） |

R1〜R4 が前の題材には無かった要求である。月次報告書は欄が並ぶ書類だったが、部会ログは**本文が主体**で、要求のほとんどが本文の構造に向く。

## 成功のイメージ（非技術）

部員がこれまでどおり Notion に部会ログを書く。回次の見出しを自分で書く必要はなく、新しいページを作った時点で `## 活動報告` `## アナウンス` `## 次回予告` の3節が入っているので、その下に `### イベント名` を足して文章か画像を置くだけでよい。**今より書く量が減る。**

書き終えたものをエクスポートして渡すと、`7月10日(金) 第47回部会` という見出しが付き、節が毎回同じ並びで、誰が書いても同じ体裁の PDF が出る。空だった次回予告の見出しは出ない。臨時に立てた「部費回収」の節も消えずに後ろに付く。

## エージェント提案（選択肢・推奨）

**論点（#22 時点）: `document` 型が `src/entex/` に未実装のまま、パッケージを先に書いてよいか。**

[issue #21](https://github.com/NPCdotcom/EnTeX/issues/21) で決めたのは `document` の設計だけで、当時の `src/entex/ir/schema.py` の `FieldType` に `document` は入っていなかった。この状態では `schema.json` が読み込めず、PDF も出なかった。

| 選択肢 | メリット | デメリット |
|--------|----------|------------|
| A: パッケージ（`schema.json` / テンプレート / examples）を先に書き、`src/entex/` の実装は別 issue に切る | 実装側が「通すべき形」を先に手に入れられる。`examples/invalid/` がそのまま実装のテスト材料になる。担当の分界（TEAM.md: `packages/` は Aster、`src/entex/` は NPC）とも合う | 実装が入るまで PDF が出ない。完了条件のうち1つが持ち越しになる |
| B: `document` の実装を待ってからパッケージを書く | 書いた直後に PDF まで確かめられる | 実装側が形の決まっていないものを実装することになり、手戻りが出る。issue #22 の「後続」節が想定している順序（`packages/` が先）と逆になる |

**推奨: A。** [issue #22](https://github.com/NPCdotcom/EnTeX/issues/22) の完了条件が「`src/entex/` を1行も触っていない」を掲げ、触る必要が出たら**直さずに報告する**と明記しているので、これはその場合に当たる。

この推奨どおり A を採り、`src/entex/` の実装は[issue #30](https://github.com/NPCdotcom/EnTeX/issues/30)（PR #32）で充足した。上の論点・選択肢・推奨は #22 時点の判断の記録として残す。

## Facts / Assumptions

**Facts**（確定している事実）:

- 部会ログの実物は2024/5〜2026/7の47本で、全数を集計済み（issue #14）。上の実測表がそれである
- メタ情報を人が書かないこと、今年度の回次を持たないことは charter §5.2 で決着済み
- 節の3つ（活動報告・アナウンス・次回予告）と、臨時の節を許すことは charter §5.1 で決着済み
- 承認・確認のフローは無い
- `schema.json` の形式は案1（ir-type-vocabulary.md §8）

**Assumptions**（まだ検証していないこと）:

- Notion の ID プロパティ（自動採番）を通算回次として使えること。**プロパティの追加は未実施**で、過去47本に付く番号が本当に通算回次と一致するかは実機で確かめていない
- 年度プロパティ（`開催日` からの4月始まりの数式）が正しい値を出すこと。仮 DB で作ったが目視確認が済んでいない
- データベーステンプレートを空の3節に差し替えれば、書く側の負担が実際に減ること。使ってもらって確かめていない
- 節の中の下位見出しの深さが2段（節の直下が1）で足りること。実測では `### イベント名` の1段が主で、まれに `#### 打ち上げ場所` が出る
